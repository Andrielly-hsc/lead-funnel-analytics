# Data card — synthetic CRM lead dataset

> Structure follows *Datasheets for Datasets* (Gebru et al., 2021). Version 1.0.0, seed 42.
> Related: [data dictionary](data_dictionary.md) · [causal model](causal_dag.md) ·
> [known issues and limitations](known_issues.md) · [ADR-0004](../adr/0004-synthetic-data-with-known-ground-truth.md).

## 1. Motivation

| | |
|---|---|
| **Purpose** | Demonstrate an end-to-end analytics workflow — pipeline, data quality, dimensional modelling, statistical and causal inference, dashboarding — on data whose *true* effects are known, so that methods can be verified rather than trusted. |
| **Question it supports** | Does a faster first response to a sales lead increase its conversion, and by how much? |
| **Created by** | Andrielly-hsc, as a portfolio project. No funding, no client. |
| **Why synthetic** | Real CRM data contains personal data and cannot be published; public lead datasets lack timestamps of first contact. Synthetic data removes both problems and adds a ground truth. |

## 2. Composition

| File | Rows (seed 42) | Grain |
|---|---:|---|
| `leads.csv` | 51 510 | one row per lead as exported (50 000 people + 500 near-duplicates + 1 010 exact duplicate rows) |
| `interactions.jsonl` | 101 734 | one row per outbound contact |
| `opportunities.csv` | 7 799 | one row per converted lead |
| `agents.parquet` | 44 | one row per agent version (40 agents, 4 team changes) |
| `campaigns.parquet` | 24 | one row per campaign |
| `_ground_truth.json`, `_truth_leads.parquet` | — | true parameters, realised effects, injection log, per-lead true values — **not visible in a real CRM** |

- **Instances are fictional companies and contacts.** Company names are random syllable
  combinations; e-mail addresses use the reserved `.example` top-level domain (RFC 2606), so
  they can never reach a real person; phone numbers are random digits. No row describes a
  real person or organisation.
- **Known defects are deliberate** (duplicates, inconsistent codes, MCAR/MAR missing values,
  clock skew, wrong import dates, late records) and logged in `_ground_truth.json`. Rates:
  [`params.py`](../../src/lead_funnel/generator/params.py) · register: [known issues](known_issues.md).
- **Sensitive attributes:** none. There are no demographic or protected characteristics of
  people. Agents are identified only by code (`A001` …) with team and seniority.

## 3. Collection (generation) process

- Generated by `lead-funnel generate --seed 42` (code in [`src/lead_funnel/generator/`](../../src/lead_funnel/generator/)).
- Arrival times follow weekday, hourly, seasonal and trend patterns in Europe/Berlin local
  time; timestamps are exported in UTC.
- Response time, conversion and opportunity value follow the causal model in
  [`causal_dag.md`](causal_dag.md); the effect of response time on conversion is fixed at an
  odds ratio of 0.85 per doubling of (1 + hours).
- Deterministic: the same seed produces byte-identical files (SHA-256 in `_manifest.json`).
- **What the generator does not model:** unmeasured confounders, seasonality of staffing,
  holidays, changes in routing rules, competitor activity, customers' own urgency.

## 4. Preprocessing, cleaning and protection

| Stage | What happens | Where |
|---|---|---|
| Ingestion | Structural contract check; violating files quarantined, never silently loaded | `ingestion/contracts.py` |
| Staging | Exact duplicates removed; spellings mapped to canonical codes; **e-mail and phone pseudonymised** (salted SHA-256) and the raw values dropped | `dbt/models/staging/` |
| Marts | Near-duplicates **flagged** (not deleted); invalid and implausible response times flagged | `int_leads__duplicates`, `int_leads__first_response` |
| Analysis | Flagged records excluded where the plan says so, with robustness checks that put them back | [`analysis_plan.md`](../../reports/analysis_plan.md) |

**Data protection (GDPR principles applied as if the data were real):**

- *Data minimisation* (art. 5(1)(c)): marts and dashboard hold no direct identifiers — only
  pseudonymous hashes needed for duplicate detection.
- *Pseudonymisation is not anonymisation* (Recital 26): hashed e-mails are still personal data
  if the salt is known; the salt is read from an environment variable and must be secret in
  production (`LF_HASH_SALT`; the default is for local use only).
- *Accuracy* (art. 5(1)(d)): the duplicate rule favours precision because wrongly merging two
  people is worse than missing a duplicate ([dedup analysis](../../reports/quality/dedup_analysis.md)).
- *Storage limitation* (art. 5(1)(e)): nothing is stored beyond the build — `data/` is
  git-ignored and regenerated from code; a real deployment would need a retention period for
  raw exports and the quarantine folder.

## 5. Uses

**Intended uses**

- Teaching and demonstrating analytics engineering, data quality and causal inference.
- Testing whether an estimation method recovers a known effect (bias, coverage).
- A realistic test fixture for pipelines and dashboards.

**Out-of-scope uses — do not**

- Draw conclusions about real lead funnels, industries, countries or channels: all
  distributions and effects are *assumptions* set in `params.py`.
- **Rate individual agents.** Agent-level KPIs depend on the leads each agent is routed;
  using them for performance evaluation would be unfair even on real data, and the dashboard
  says so next to the agent table.
- Treat the pipeline value (expected deal value) as revenue.

## 6. Distribution and licence

- Code and documentation: MIT licence ([`LICENSE`](../../LICENSE)). Generated data is not
  committed; anyone can regenerate it with the same seed.
- No personal data is distributed.

## 7. Maintenance

- Maintained in this repository; changes to the generator are versioned and the data
  dictionary is regenerated from code (a test enforces it).
- To change assumptions, edit `params.py`; the ground-truth file records the parameters of
  every run, so results always state which assumptions produced them.
